# Implementation Plan 29 — MCP Host Compatibility

**Status:** 2026-09-17 — **W1 COMPLETE LOCALLY, NOT YET DEPLOYED.** Backend suite 45 files / 970 tests green (966 before W1 — the plan's stated 907/42 baseline was Plan 28 W5's figure, stale by three files/59 tests that landed in Plan 28's later waves); `git diff --check` clean; README untouched. Production still serves the pre-W1 result shape until the owner runs `/deploy`. The W1 record has the evidence. Approved for implementation 2026-09-17 by owner ruling; written at `d4a485e` (Plan 28 closed) from the first third-party host to use the hosted MCP: a personal AI companion (a separate, unrelated repository — its identity is irrelevant here; call it "the text-only host") that reads only the `content[].text` half of every tool result and rebuilds each tool's `inputSchema` from its top level. Both of that host's defects were fixed in its own repository the same day. **This plan makes Trippy's MCP correct for any host regardless**, because the next client the owner or anyone else connects will have its own quirks, and "works in Claude Code" is not a compatibility claim.

**Origin.** Plan 28 W2 chose "every tool returns `structuredContent` (the object) **plus** a short text summary" and every real-client run (Claude Code, Codex CLI, MCP Inspector, W5's matrix) read the structured half, so the design assumption was never tested. On 2026-09-17 the text-only host ran `prepare_draft` for a hotel with `address` instead of `destination`, received the text `"1 booking: hotel … ; a stop will be created on 2026-09-25; 1 blocker."`, and could not tell its user what the blocker was — the `missing_required_field` issue for `bookings[0].destination` lived only in `structuredContent.issues`. It then called `get_apply_status` with `draftId: null` (its schema converter had told the model optional fields are nullable) and the ajv validator refused `null` for `type: string`. Two Trippy-side gaps, both general:

- **G-29-1 — The text channel is not self-sufficient.** Ids, URLs and issue detail live only in `structuredContent`. A text-only host cannot call `get_trip` after `list_trips` (no trip id in the text), cannot call `apply_draft` after `prepare_draft` (no `draftId` in the text), and cannot explain a refusal. The MCP specification says a tool returning `structuredContent` SHOULD also return the serialised JSON in a `TextContent` block for backwards compatibility; Trippy did not.
- **G-29-2 — Optional means "omit", never "null".** Every optional property is declared `type: "string"` (or array/integer/object) without `null`. Hosts that build their tool schemas through Pydantic, zod `.nullable()`, or OpenAI strict mode present optionals as nullable, and models then send `null` for "not applicable" — `confirmationRef: null` on a hotel with no reference is the natural thing for a model to emit. Trippy refuses the whole call.

**Scope in one sentence:** make every `/mcp` tool result usable by a host that reads only text, make every optional input accept `null` as "absent", and say in the summary what each blocker and warning is — without changing a single write path, fingerprint, TTL, access rule or the seven-tool set.

**Not in scope.** No new tools, no OAuth (D-28-1), no model calls, no change to `structuredContent` shapes (existing hosts keep parsing exactly what they parse today), no change to `mcp_drafts`/`mcp_upload_tickets`, no migration.

## Validated facts — established 2026-09-17 at `d4a485e`, do not re-derive

**F-29-1 — Every tool result is assembled inline in `services/mcp/tools.js`.** Seven `server.registerTool` handlers build `{ content: [{ type:'text', text }], structuredContent }` by hand at ~14 return sites, plus the shared error shapes `requireScope`, `notFoundResult`, `draftNotFoundResult`, `bookingNotFoundResult`, `errorResult`, `applyErrorResult`. There is no single result constructor, so the text/structured relationship is a convention, not a guarantee.

**F-29-2 — The summaries carry counts, not issues.** `summarizeDraft` (`validate.js:497-519`) appends `"N blocker(s)"` / `"N warning(s)"` and nothing about which; `summarizeDelete` (`prepareDelete.js`) is the delete-side equivalent. Issue objects carry `severity`, `code`, `field`, `bookingIndex`, `message`, and sometimes `suggestion`/`existingBookingId` — everything a summary needs is already there.

**F-29-3 — Schemas go through `fromJsonSchema` from `@modelcontextprotocol/server` (ajv underneath).** `type: "string"` refuses `null`; `type: ["string","null"]` accepts it; an `enum` must list `null` explicitly for a null value to pass. Optional properties in the seven schemas: `list_trips.query/includePast`; `get_trip.include`; `prepare_draft.bookings[].{confirmationRef,bookingSource,endDatetime,origin,destination,terminalOrStation,originTz,destinationTz,detailsJson,showInItinerary}` and `target`/`source` sub-fields (those two are declared as bare `type: object` with prose descriptions, so ajv does not validate their insides); `get_apply_status.draftId/idempotencyKey`; `prepare_delete.deleteExpenseIds`.

**F-29-4 — Handlers already mostly treat `null` as absent.** `validate.js` checks `!== undefined && !== null && !== ''` for datetimes and time zones, `?? null` for pass-through fields, and `validateDelete` maps `null` → `[]` for `deleteExpenseIds`. The exception is `source.sourceBookingIndex !== undefined` (`validate.js:99`): a `null` there becomes a blocker. `get_apply_status`'s `(draftId && idempotencyKey) || (!draftId && !idempotencyKey)` treats `null` as absent already — the refusal came from ajv before the handler ran.

**F-29-5 — Tests.** `backend/tests/mcpTools.test.js` asserts on `structuredContent` and on `inputSchema.properties` presence; `mcpClient.e2e.test.js` drives a real SDK client over HTTP. Baseline at `d4a485e`: backend 42 files / 907 tests (Plan 28 W5 record). `npm test` = `vitest run`.

**F-29-6 — `README.md` has an uncommitted owner edit** ("Connect Your Own AI Tools") that predates this plan. It is the owner's; this plan's commit must not include it and must not touch README.

## Decisions (stamp in the code they govern; one pointer row each in `docs/DECISIONS.md`)

- **D-29-1 — Every tool result's `content` carries the structured result as text.** One constructor, `toolResult({ text, structuredContent, isError })` in `services/mcp/tools.js`, returns `content: [ {type:'text', text}, {type:'text', text: JSON.stringify(structuredContent)} ]` whenever `structuredContent` is present, and every return site — success, refusal, not-found, scope error — goes through it. A second block (not appended to the first) so a host that shows blocks separately keeps the human sentence readable and a host that de-duplicates against `structuredContent` can parse the block on its own. This is the MCP spec's backwards-compatibility guidance, applied mechanically so no future tool can forget it.
- **D-29-2 — A summary names every blocker and warning.** `summarizeDraft` and `summarizeDelete` list each blocker and warning as `code` + location (`bookings[i].field` / `field`) + `message`, and each info item as `code` + location (+ `suggestion` when present). The count-only form is gone. The summary stays one paragraph; it is the sentence a human reads in any host's tool-call panel.
- **D-29-3 — Optional means nullable; `null` is "absent".** Every optional property in every tool schema accepts `null` (`type: [<t>, "null"]`, with `null` added to any `enum`), applied by one recursive helper at schema-definition time so a new tool cannot opt out by forgetting, and every handler treats `null` exactly as omitted. Required properties are untouched — a required `null` is still a validation error, and that is the right answer.
- **Per-type required fields are stated in the schema text.** `prepare_draft`'s `bookings` description gains one sentence: "Required per type: flight/train/bus/ferry need origin and destination; hotel needs endDatetime and destination; other needs only title and startDatetime." It mirrors `TYPE_REQUIRED_FIELDS`; keep the two in step. No marker — it is documentation, not a ruling.

## W1 — Self-sufficient text, named issues, nullable optionals

**Status:** COMPLETE LOCALLY 2026-09-17; deployment pending (owner-triggered).

**Files.** `backend/src/services/mcp/tools.js`, `backend/src/services/mcp/validate.js`, `backend/src/services/mcp/prepareDelete.js`, `backend/tests/mcpTools.test.js`, `backend/tests/mcpClient.e2e.test.js` (one assertion), `docs/ENGINEERING.md` (Hosted MCP section), `docs/DECISIONS.md`, `Implementation Plan 28 Hosted MCP.md` (one pointer line under "Known-and-accepted"), this plan.

**Steps.**

1. **`toolResult` constructor (D-29-1).** Add it to `tools.js`, stamp the marker, and route every return through it — the seven handlers' success paths, `errorResult`, the three not-found helpers, `requireScope`, and `applyErrorResult`. Serialise with `JSON.stringify(structuredContent)` (no indentation — bytes matter on every call). No handler may build a `content` array by hand afterwards; grep `content: [` in `tools.js` must find only the constructor.
2. **Named issues (D-29-2).** Rewrite the issue tail of `summarizeDraft` and `summarizeDelete`: blockers first, then warnings, then info. Location is `bookings[<bookingIndex>].<field>` when both are present, `<field>` when only the field is, the code alone otherwise. Example output for the originating case: `1 booking: hotel "Frasers House, a Luxury Collection Hotel, Singapore" 2026-09-25T15:00 → 2026-09-26T12:00; a stop will be created on 2026-09-25; 1 blocker: missing_required_field at bookings[0].destination — destination is required for a hotel; 1 note: timezone_unknown at bookings[0].destinationTz.` Stamp the marker on `summarizeDraft`.
3. **Nullable optionals (D-29-3).** Add `withNullableOptionals(schema)` (in `tools.js` or a small `schema.js` beside it — one place): walks `properties` recursively (into `items` and nested `properties`), and for each property not listed in that object's `required`, adds `"null"` to `type` (string or array form) and to `enum` when present. Wrap every `fromJsonSchema(...)` call in `tools.js` with it. Fix `validate.js:99` (`sourceBookingIndex`) and audit every other `!== undefined` in the MCP services so `null` behaves as omitted. Stamp the marker on the helper.
4. **Per-type required sentence** in the `bookings` schema description (see Decisions).
5. **Tests.** In `mcpTools.test.js`: (a) for every tool call the suite already makes, assert `content.length === 2` and `JSON.parse(content[1].text)` deep-equals `structuredContent` — write it as one shared assertion helper and apply it to every existing result assertion, so the contract is checked wherever a result is checked; (b) a `prepare_draft` hotel with `address` and no `destination` → `content[0].text` contains `missing_required_field at bookings[0].destination`; (c) `get_apply_status` with `{ draftId: null, idempotencyKey }` → the pending/applied result, not a validation error; (d) `prepare_draft` with `confirmationRef: null`, `originTz: null`, `source: { kind:'screenshot', sha256: null, sourceBookingIndex: null }` → validates as if omitted; (e) the schema walker: every optional property in every registered tool's `inputSchema` lists `null` in its `type`, and no required property does. In `mcpClient.e2e.test.js`: one assertion that a real client sees two text blocks on `list_trips`.
6. **Docs.** `docs/ENGINEERING.md` → Hosted MCP (Plan 28) section: one bullet, "**Host compatibility contract (Plan 29).** Every result carries the structured object as a second text block (D-29-1), summaries name each issue (D-29-2), optional inputs accept `null` (D-29-3). Never assume the host reads `structuredContent`; never assume it omits an optional rather than sending `null`." `docs/DECISIONS.md`: three rows under "Decisions anchored in code". Plan 28 → "Known-and-accepted, do not report as bugs": one line pointing here. Update this plan's status line and the W1 record.
